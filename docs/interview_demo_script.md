# Five-minute Microsoft Solution Engineer demo

This project uses synthetic retail data and fictional company policies for demonstration purposes.

**Audience:** a customer-focused technical interview. Rehearse the narration at
a natural pace; allow time for clicks and the actual model response. Read live
values rather than memorizing a Case ID, KPI, or model answer.

## Before presenting

- Use synthetic data and the configured existing DeepSeek-V4-Flash deployment.
  Keep credentials, terminal environment output, and hidden reasoning off screen.
- Run `python -m pytest -q` and `python scripts/test_foundry.py` before the call.
  Confirm network access, quota, and the live RAG question.
- Run `python -m streamlit run app.py`. Have the app and enterprise architecture
  diagram ready. Only reset deliberately: it removes previously created cases.
- Have [the genuine screenshots](../screenshots/) available as a clearly labelled
  recorded fallback. Never present a saved image or mocked answer as live inference.

## 0:00-0:40 | Customer business challenge

*Show the application, with no credentials visible.*

FreshMart is a fictional Australian retailer with six stores. Its service team
repeatedly answers produce-policy questions, while managers review complaints,
inspections, and sales in separate places.

I focused on one customer journey: someone bought mouldy strawberries from
Chatswood. They need clear guidance and a reliable way to report the problem.
The manager needs to see that report alongside operational evidence.

Everything here is synthetic. The goal is not to automate refund approval; it
is to connect trustworthy support with a traceable review process.

## 0:40-1:15 | Why Microsoft Foundry

*Point briefly to the implemented architecture.*

I chose Microsoft Foundry for hosted model inference, using one deployed
DeepSeek-V4-Flash model. I use retrieval-augmented generation because policies
change: I want an answer tied to a current document, rather than relying on
what a model might remember.

For this small POC, five documents and SQLite full-text search are enough.
That keeps the solution simple and inspectable. Azure AI Search is an enterprise
upgrade, not something I have already implemented.

## 1:15-2:05 | Live grounded answer

*In Customer chat, submit:*

> I bought strawberries from your Chatswood store yesterday, but some of them
> were mouldy. Can I get a refund?

*Wait for the genuine response, then expand Policy sources used.*

This request retrieves relevant policy passages and calls the actual Foundry
deployment. Here are the original source title, section, and excerpt.

Notice the distinction: the policy can support submitting a review request,
but it cannot establish this customer's final refund decision. A supported
negative answer, such as no refund guarantee, is different from missing evidence.
The assistant can point to the complaint form; that guidance does not create a case.

I validate source identifiers and use a second bounded check with the same model.
That adds latency and is not a proof against hallucination. If inference fails,
the application shows an error rather than inventing an answer.

## 2:05-2:50 | Confirmed complaint submission

*Open Quality complaint. Select Chatswood and Strawberries, use yesterday's
purchase date, and enter a synthetic mouldy-strawberry description. Review,
tick confirmation, and submit.*

The customer now chooses whether to report the concern. Store and product
choices come from the database. They review the details and explicitly confirm
before anything is written.

Python, not the language model, validates and saves this case in a transaction.
The displayed Case ID is the actual database identifier, and the case is Open.
A unique submission token prevents reruns or retries from creating another case.
No refund has been approved and no payment has been initiated.

## 2:50-3:40 | Manager Dashboard

*Select Store Manager Dashboard, then NSW, Chatswood, and Strawberries.
Refresh and locate the new Case ID.*

The same case is now visible to the manager. These cards and charts are
calculated from SQLite, not generated by the model.

Freshness uses passed kilograms divided by inspected kilograms, not sales as a
proxy. Revenue growth compares equal-day periods and becomes unavailable when
the baseline is invalid.

The peer chart keeps other matching stores visible. I can compare the selected
store's inspection pass rate and complaint count using the values on screen.
These signals justify investigation, not a claim that freshness caused a sales
change. Complaint counts also need volume normalization before stronger conclusions.

## 3:40-4:15 | Business value

*Keep the dashboard visible.*

The demonstrated value is a connected process: grounded guidance, confirmed
case capture, and visibility of a new complaint without manually moving it
between systems.

For a customer pilot, I would agree a baseline for handling time, policy-answer
accuracy, submission completion, and time to manager visibility. I would also
measure false refund promises, review turnaround, and cost per interaction.
I have not measured real savings or customer satisfaction improvements with
this synthetic dataset.

## 4:15-5:00 | Enterprise proposal and close

*Show the proposed enterprise architecture.*

For a real retailer, I would evaluate Copilot Studio for the service agent,
Foundry and Azure AI Search for governed RAG, Power Automate for review routing,
Azure SQL for case data, and Power BI for management reporting.

Microsoft Entra ID would help protect staff access, with server-side
authorization separating public policies from internal sales and complaints.
Azure Monitor would track latency, errors, and workflow health without exposing
credentials or unrestricted customer content.

Those are proposed services, not implemented features. Before production, I
would validate security, policy governance, identity, recovery, licensing, and
measurable outcomes. The POC's purpose is to prove the customer journey and
make those trade-offs concrete.

## If something fails during the demo

State the observed failure plainly. Do not repeatedly submit or invent a refund
answer. Explain the explicit error, use recorded screenshots only as recorded
evidence, and demonstrate complaint persistence and dashboard calculations
independently if those systems remain available.

## Useful follow-up answers

| Question | Short answer |
|---|---|
| Why not fine-tune the policies? | Versioned retrieval can update evidence without retraining and preserves inspectable sources. |
| Why SQLite and Streamlit? | They keep this small proof of concept understandable; they are not the proposed public production platform. |
| Is this a secure manager portal? | No. The current tabs have no authorization boundary; production must separate and authorize internal access. |
| How do you know the answer is correct? | Validate citations, test known/unknown questions, evaluate sampled answers with policy owners, and acknowledge same-model verification limits. |
| Does the dashboard prove a cause? | No. Inspect the signal and investigate; account for sampling, exposure, and other explanations. |
